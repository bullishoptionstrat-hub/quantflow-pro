# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Architecture

QuantFlow Pro is an options-flow terminal split into two independently deployed services plus Supabase:

```
Next.js 14 frontend (Vercel)  <-- REST + Socket.IO -->  Node/Express backend (Render)
                                                                    |
                                                              Supabase (Postgres + RLS)
```

- **`frontend/`** — Next.js 14 App Router, TypeScript, Zustand (`store/useStore.ts`) for client state, Socket.IO client (`lib/socket.ts`) for the live flow feed, Supabase SSR client for auth. Routes live under `app/` as one directory per feature (`flow`, `dark-pool`, `gex`, `heat-map`, `calculator`, `optimizer`, `power-alerts`, `watchlist`, `macro`, `news`, `settings`, `(auth)`). `middleware.ts` gates every non-auth, non-`/api` route behind a Supabase session, redirecting to `/login` when absent — or behind a demo cookie when demo mode is on (see the note below).
- **`backend/`** — Express + Socket.IO server (`src/server.ts`). `startIngestion(io)` (`src/ingestion/index.ts`) drives a pull/push pipeline from many market-data connectors (`src/ingestion/connectors/*` — Tradier, Polygon, Finnhub, plus 13 free-tier connectors: FlashAlpha, MarketData.app, Schwab, Tastytrade, TwelveData, FMP, CoinGecko, FRED, Reddit, NewsAPI, CBOE, Yahoo, Stooq). Every source normalizes to a `RawPrint` and funnels through `ingestPrint()` in `src/ingestion/flowEngineAdapter.ts`, which publishes the contract's NBBO, feeds the trade to the flow engine (`src/flow-engine/`), and maps finalized signals onto the wire shape. Signals are batched by `emitSignals` (100ms window) and broadcast as a **single global `flow_batch`**. REST routes under `src/routes/*` mirror the API reference below. When no live vendor keys are configured, ingestion falls back to an always-on simulation mode so the app still functions.
- **`backend/src/flow-engine/`** — the classification + scoring engine, vendored from `quantflow-modules/flow-engine` (the module is ESM; the backend is CJS, so it is copied rather than imported, with relative-import extensions stripped). It is byte-identical to the module apart from an added `resetDaily()`. **Change the engine here, and mirror it to the module** — or the module's test suite stops being a valid baseline for what ships.
- **`backend/src/enrichment/`** — the web-enrichment seam. `firecrawl/` is vendored from `quantflow-modules/firecrawl/src/services/firecrawl` (ESM module, CJS backend, so copied with relative-import extensions stripped — **change one, mirror it to the other**); `index.ts` is what the backend adds around it. Two rules live there and nowhere else: enrichment is **demand-driven, never scheduled** (its calls cost metered Firecrawl credits, so nothing fetches unless a request asks), and `AUTH` / `INSUFFICIENT_CREDITS` **latch the service off** until restart rather than retrying against a key that will not recover. Surfaced at `GET /api/sentiment/context`, `/context/status`, and `/regulatory/:slug`, and reported under `enrichment` in `/api/health`. With no `FIRECRAWL_API_KEY` it reports `disabled` and the rest of the app is unaffected.
- **`backend/src/provenance/`** — the data-rights registry. Every external dataset is classified per business mode and per capability (`DISPLAY` vs `PERSIST`), with the publisher's restriction quoted verbatim and the terms URL/read-date recorded. It **fails closed**: `UNVERIFIED` is refused (uncertainty resolves to refusal, not permission), an unregistered source is refused, and a malformed `BUSINESS_MODE` throws rather than degrading to either branch. `DISPLAY` and `PERSIST` are separate because the risk is separate — reading a delayed quote once is not the same act as accumulating a database out of it. `classify()` is the `PERSIST` decision; `mayOperateConnector()` is the `DISPLAY` one and gates whether a connector runs at all (see the note below).
- **`backend/src/persistence/`** — the durable signal history, and the reason the product can ever have a track record. `identity.ts` computes `decisionAt = max(lastEventAt, receivedAt, emittedAt)` (never `ts`, the first print — see below) and the content hash that is a signal's real identity; `recorder.ts` is the one path from a classified signal to storage and applies the rights gate; `grader.ts` grades M15/H1/D1 outcomes scheduled from `decisionAt`; `memoryStore.ts` is the reference implementation of the policy and `supabaseStore.ts` mirrors it. Store selection is reported in `/api/health` under `history` — a deployment that is silently discarding everything is the failure this module exists to make impossible to have by accident.
- **`supabase/`** — `schema.sql` (source of truth, run manually in the Supabase SQL editor) plus `migrations/` for incremental changes. `gate-proofs.sql` is re-runnable evidence that the signal-history constraints actually refuse what they claim to (`psql -d <db> -f supabase/gate-proofs.sql`; every `ERROR:` in its output is a pass). Tables are RLS-protected; `user_profiles` extends `auth.users`, and `api_keys.key_value` is a plaintext column intended to be encrypted via Supabase Vault in production (not yet wired up — treat as sensitive).
- **`quantflow-modules/`** — `flow-engine/` is the canonical home of the classification engine (sweep/block/split/multi-leg, NBBO side inference, deterministic unusualness scoring, outcome tracking) and holds the engine test suite plus the Polygon replay adapter for validating against real historical tape. It is **now integrated** into the backend via the vendored copy described above. `firecrawl/` is a web-enrichment module (FINRA doc sync, news context, research workflows) and is **now integrated** via a vendored copy at `backend/src/enrichment/firecrawl/` — same arrangement as the flow engine, and the same mirroring obligation. Check whether work belongs here vs. in `backend/src/ingestion` before duplicating logic.
- Root-level `qf-firecrawl (1).zip`, `qf-flow-engine.zip`, `quantflow.zip` are uploaded archives, not part of the working tree — the unpacked, current sources are `quantflow-modules/` and this repo itself.

## Commands

```bash
# Can this deployment accumulate a track record? (backend/tools/collection)
cd backend && npm run collection:doctor                       # config only
npm run collection:doctor -- --url http://localhost:3001      # plus live state

# Preview — the UI against a captured backend, in ~35MB (backend/tools/preview)
cd backend && DEMO_MODE=1 npm run dev                 # in another shell
npm run preview:capture -- --out .preview/cap         # record what it says
cd ../frontend && npm run build
cd ../backend && DEMO_MODE=1 npm run preview -- --cap .preview/cap --site ../frontend/.next

# Frontend
cd frontend && npm install
npm run dev      # http://localhost:3000
npm run build
npm run lint      # next lint
npm test          # vitest run — formatters, empty states, and the fetching pages
npm run verify    # tsc --noEmit && vitest run

# Backend
cd backend && npm install
npm run dev       # ts-node-dev, auto-restart, http://localhost:3001
npm run build      # tsc -> dist/
npm start          # node dist/server.js
npm test          # tsx --test test/*.test.ts — adapter/wire-mapping tests
npm run typecheck  # tsc --noEmit


# flow-engine module (canonical source; backend ships a vendored copy)
cd quantflow-modules/flow-engine && npm install
npm test        # tsx --test test/engine.test.ts test/outcome.test.ts
npm run typecheck
```

Environment setup: copy `.env.example` to `frontend/.env.local` and `backend/.env` respectively (see README's "Environment Variables Reference" for the full key list per service). The backend's authoritative key list is the root `render.yaml`, held to `src/` in both directions by `backend/test/renderBlueprint.test.ts` — a variable read by no code and a variable declared nowhere are both failures there. Run `supabase/schema.sql` **and then every file in `supabase/migrations/` in filename order** in the Supabase SQL editor before first run (RLS-protected tables; the app expects them to exist). Both are needed: `schema.sql` creates the seven application tables and **none** of the four the recorder and grader write to — `signal_history`, `signal_outcomes`, `signal_write_incidents`, `collection_gaps` live in `migrations/20260829120000_signal_history.sql`. `backend/test/schemaSetup.test.ts` holds the instruction to the tables `supabaseStore.ts` actually addresses.

Deployment: frontend → Vercel (root directory `frontend`, rewrites in `frontend/vercel.json` must point at the deployed backend URL); backend → Render via the root `render.yaml` Blueprint (`rootDir` is set there). Render's free tier sleeps services after 15 minutes of inactivity.

## Notes

- **Demo mode** is a read-only unauthenticated path, **off unless both `NEXT_PUBLIC_DEMO_MODE=1` (frontend) and `DEMO_MODE=1` (backend) are set**. Two independent conditions gate every step, so neither a stray cookie nor a stray header opens anything on its own: `/demo/enter` 404s, the `qf_demo` cookie is ignored by `middleware.ts`, the login button is not rendered, and `requireAuthOrDemo` 401s without `X-QuantFlow-Demo: 1`. **`/api/chain` and the three enrichment endpoints stay on plain `requireAuth`** — they return entitled vendor data or spend metered credits, and demo traffic must never reach them. When adding a route, put it on `requireAuthOrDemo` only if it costs nothing per call. The `DemoBanner` is deliberately loud and non-dismissible: the terminal is styled to look like a live institutional product and a demo session is showing simulated prints.
- **Demo mode could not start on a deployment with no Supabase project — the only kind it exists for.** Two places built a Supabase client eagerly, and `createClient`/`createServerClient` **throw** when either env var is missing. `middleware.ts` constructed one *before* it checked the demo cookie, so every gated route returned **500** rather than redirecting to `/login`; and `lib/supabase.ts` constructed one at module load with `!` assertions, which every page reaches (`apiFetch`, `socket`, `DemoBanner`, both auth pages) — so the login page that **offers the demo button** threw before it could render. Measured: `GET /flow/ → 500 Your project's URL and Key are required` and `GET /login/ → 500 supabaseUrl is required.` The escape hatch was behind the door it was meant to open. The stand-in **does not fake a session**: `getSession()` answers `{ session: null }` because that is the truth and `apiFetch` asks it on every request; `signInWithPassword` returns a *stated* configuration error naming the two variables and pointing at demo mode, because that question genuinely cannot be answered and a blank page would send the reader after the wrong problem; and `onAuthStateChange` returns a real `unsubscribe`, because `lib/socket.ts` calls it in `disconnectSocket` and a bare object would move the crash rather than remove it. Skipping the client is not a weakening — with no project there is no session to verify — and the demo path is still the same two independent conditions. Found by opening the app in a browser, which is the only way it surfaces: every test in the suite runs with the client mocked or the env already set.
- Tests cover the flow engine (`quantflow-modules/flow-engine`, 24 tests) and the backend seams (`backend/test`, 430 tests: the adapter, the health-error formatter, the enrichment latch, the demo-mode gate, the connector credential table, the vendored-copy mirror guard, the prohibited-host scan, the dead-source guards, the Blueprint drift check, the socket handshake gate, the frontend wire contracts (now including the news page's three panels and the normalized news wire), plus the rights registry, the connector gate, signal identity/decision time, the store, the recorder, the grader, the unanswered-count refusal, and an end-to-end history integration suite) — both `node:test` via `tsx`. `npm run verify` in `backend/` runs typecheck (src **and** test, via `tsconfig.test.json`) then the suite.
- **`frontend/test/` is Vitest + Testing Library (127 tests), and covers what the backend suite structurally cannot.** `wireContract.test.ts` reaches across the directory boundary and matches text against source, which catches a field name drifting from the API; it cannot catch a field read correctly and *displayed* wrongly. That is how `cryptoPrice` shipped rendering SHIB at 0.0000058 as **$0.0000** — caught by eye in a screenshot, not by a test. The formatters now live in `lib/format.ts` (they were module-local inside `app/macro/page.tsx`, so untestable by construction), and the component tests render against **the same recorded fixtures** in `backend/test/fixtures/`. Config is `vitest.config.mts` — `.mts` because `@vitejs/plugin-react` is ESM-only, with `esbuild: { jsx: 'automatic' }` because `tsconfig.json` sets `jsx: preserve` for Next and Vitest has no Next. It runs `pool: 'forks', singleFork` deliberately: the default worker pool starts a jsdom per thread and will not fit alongside a Next build on a small box, and a suite that cannot be run is worth nothing.
- **The flow event wire shape is `frontend/lib/types.ts` `FlowEvent`** — snake_case, shared by `/api/flow` and the `flow_batch` socket event. (Before the engine integration the backend emitted an unrelated camelCase shape that the frontend silently failed to read.) Change it in both places at once; `getFlowStats()` and `routes/flow.ts` filter on these field names and would return empty results, not errors, if they drift.
- **`toWireEvent` filled four fields with zero when it had no data for them, and classified a strike against one of them.** A print arriving without a chain snapshot published `iv: 0`, `delta: 0`, `open_interest: 0` and `spot_price: 0`; `moneynessOf` then opened with `if (!(spot > 0)) return 'OTM'`, so the strike was *classified against that zero* and the signal was labelled **OTM on no evidence**. Three states could not express "we do not know", so it picked one and stated it with the confidence of a computed answer. The figures are `number | null` now and `moneyness` has a fourth state, `UNKNOWN`. **Nothing in the terminal renders any of them today — which is the hazard, not the consolation**: a field carrying a fabricated default is one binding away from showing a zero as a fact, which is exactly what `ml_score` was and what `MarketSnapshot` would have been. **`UNUSUAL_SCORE` now has one home.** `is_unusual` was `sig.score >= 75` in the adapter while the frontend's `isPowerAlert` read `e.is_unusual && e.heat_score >= 75` — a conjunction whose second term is *implied by the first*, restating the backend's threshold in a second place while looking like an independent condition. The power alerts page then described its trigger as two tests, which was true and misleading at once. The constant is exported from `flowEngineAdapter.ts`, `isPowerAlert` reads the published flag alone, and the page names one condition.
- **`ClassifiedSignal.ts` is the FIRST print in the cluster and is deprecated for any measurement.** A signal assembled from a 500 ms burst was not actionable at that burst's first tick, so measuring an outcome from there hands the backtest the burst duration plus the feed latency as free information and every excursion comes out flattering. Use `decisionAt`. The invariant `decisionAt >= lastEventAt >= firstEventAt` is enforced in `identity.ts` (throws), in the store, and as a `CHECK` constraint. Signals with no receipt clock (replay) get `decisionBasis: 'EVENT_TIME_ONLY'` — a lower bound crediting zero latency — and are excluded from published rates rather than pooled with observed ones.
- **The outcome tracker graded the wrong leg, from the wrong clock.** `buildSignal` takes `ClassifiedSignal.side` from the **highest-premium** leg but stores `legs` in the order their contract+side groups were first seen; `outcome/tracker.ts` read `legs[0]` at three call sites and paired it with `signal.side`. So a bought $102k SPY call alongside a bought $2.2k put — a long strangle — graded **BEARISH**, because the small put printed five milliseconds earlier. Single-leg signals are unaffected, which is why it survived: it is only wrong on the structures whose direction is hardest to read by eye. `dominantLegOf()` is the one helper, and `outcome.test.ts` constructs that structure and asserts both premises before the conclusion. **This entry called it "a bullish risk reversal" until 2026-09-16, and it is not one** — driving the fixture reports `side=BUY` on *both* legs, because both are lifted at the ask. A risk reversal is long one wing and **short** the other; two longs is a strangle, a bet on movement rather than on direction. The finding is untouched — the tracker really did read `legs[0]` and pair it with `signal.side` — but the structure was misnamed in the one entry about reading structures correctly, which is the joke telling itself. The tracker also took its entry marks at **`signal.ts`** and scheduled every checkpoint from it — the FIRST print in the cluster, which this file deprecates for any measurement — and then stamped the entry snapshot `ts: signal.ts` while the marks were fetched at a different instant, which is the manufactured freshness `RawPrint.quoteTs` exists to prevent. `decisionTimeOf()` is `max(lastTs, receivedAt, emittedAt)` requiring **both** clocks, and records `OBSERVED` / `EVENT_TIME_ONLY` on the tracked row. That rule now has two homes — `persistence/identity.ts` for production and the module for its standalone tracker, which cannot import across that boundary — so **`backend/test/outcomeDecision.test.ts` holds them to agreement** on every combination of clocks, the way `vendorMirror.test.ts` holds the vendored copy to its source. `buildReport` carries `labelRule: 'MAX_EXCURSION'` and an `eventTimeOnly` count on the payload: the grading precedence is unchanged (a signal that reached the win threshold at any checkpoint is POSITIVE **even if it reached the loss threshold first**), but that is a best-moment measure and not what a held position would have returned, so it is stated rather than left to the reader. **`backend/src/persistence/` is the production recorder and grader**; nothing in `backend/src` imports `OutcomeTracker`, and both index files now say so.
- **The score's clamp was applied silently, so the breakdown did not add up to the score beside it.** Components floor at `premium: 3` and `ambiguousPenalty` is -15, so a low-premium signal whose side could not be inferred produced a raw of **-12** against a published score of 0. `scoreBreakdown` crosses the wire as `score_breakdown` and the power alerts page renders it term by term under the 22px heat number, which invites exactly the addition that would not have reconciled. The clamp is now a term (`clamp: +12` in that case), so every breakdown sums to its own score; `engine.test.ts` asserts it across a matrix of kinds, premiums, side-certainty, exchange counts and repeat hits, and fails if the matrix never reaches the clamped case. The upper bound cannot bite today — the six components sum to exactly 100 — but a threshold raised past that now shows as an overflow term instead of being swallowed.
- **A signal's identity is its content hash, not `ClassifiedSignal.id`.** The engine id is `sig_<seq>_<ts>` and the sequence restarts at 1 on every process boot, so it is bookkeeping only. A duplicate key carrying *different* content is a `HISTORY_COLLISION`: recorded as an incident, and the stored row is kept. Treating it as idempotent — the usual default — silently accepts a rewrite of recorded history.
- **`/api/track-record` publishes no rate below n=30 graded outcomes** (`INSUFFICIENT_SAMPLE`), excludes synthetic signals entirely while counting them where a reader can see them, and reports `UNGRADED` outcomes rather than dropping them. Most `UNGRADED` rows are `AMBIGUOUS`-side signals — the ones a less careful system would guess a direction for. Adding a connector means adding its `source` string to both `SOURCE_TO_DATASET` and `INGESTION_SOURCES` in `test/rights.test.ts`; an unmapped source is refused silently, which reads as "nothing is being recorded".
- **A connector whose dataset is `PROHIBITED` for `DISPLAY` is never started.** `mayOperateConnector()` in `provenance/rights.ts` is the gate; `startConnector`, `startCboeOptions` and `startOcc` consult it *before* calling `start()`, because `start()` is what issues the request and the request is the act the terms forbid. The source then reports `refused` on `/api/health` — a **fourth status**, distinct from `disabled` (no credentials) and `error` (the vendor said no), so nobody tries to fix it with an API key — and `ingestion.rightsRefusals` carries the quoted restriction, the terms URL and the read date. Today that is Yahoo alone. There is deliberately **no override env var**: a bypass over an established, quoted prohibition lets the refusal be switched off by whoever is least likely to have read the terms.
- **The gate is narrower than `classify(id, 'DISPLAY')` on purpose, and must stay that way.** It refuses `PROHIBITED` only. `UNVERIFIED` sources (CBOE, OCC, FINRA) keep running and keep reporting their class — the registry's own reasoning is that an unverified source "is a much worse basis for a permanent record than for an ephemeral panel", and the Cboe entry concedes the asymmetry when it says `PERSIST` is refused "anyway". If the gate refused `UNVERIFIED` too, `DISPLAY` and `PERSIST` would resolve identically for every dataset and the two-axis design would be dead code; `test/connectorGate.test.ts` has a canary that fails if that ever happens. An **unregistered** source is not stopped either — FRED, CoinGecko, Reddit, NewsAPI, Stooq, TwelveData, FMP and FlashAlpha emit no prints and have no dataset entry, and refusing them here would take out the macro/news/sentiment pages over a registry coverage gap rather than a rights finding. They remain refused for `PERSIST`, which is where an unregistered source actually does damage.
- **The root `render.yaml` is the only Blueprint, and it is checked against the code.** `backend/render.yaml` was a second, stale copy declaring the same service — no `BUSINESS_MODE`, a pinned `PORT` (Render injects it), and none of the connector credentials — so whichever one Render was pointed at, the other was a trap. It drifted in both directions and neither was visible from inside the code: fourteen free-tier connector credentials were read by `src/ingestion/connectors/*` and declared nowhere, so a Blueprint deploy had no slot for them and those sources reported `disabled — no credentials` in production with no dashboard fix; while `ALPACA_KEY`/`ALPACA_SECRET` (there is no Alpaca connector) and `UPSTASH_REDIS_REST_URL`/`_TOKEN` (the rate limiter is in-memory and no redis client is installed) were declared, documented in the README and `.env.example`, and read by nothing. `renderBlueprint.test.ts` fails on either direction. **`YAHOO_ENABLED` is deliberately undeclared** — the rights gate refuses that connector before `yahoo.ts` reads the flag, so an entry would advertise a switch that does nothing.
- **A source that is down must never present itself as data**, and three of them were. Stooq answers with a JavaScript browser-verification page instead of its CSV (HTTP **200**, HTML body) — the parser's only guard was `lines.length < 2`, which a four-line challenge page clears, so twelve quotes with `close: 0` were cached every ten minutes while `/api/health` said `connected`. Cboe's `options_volume.json` returns **403**, and a bare `catch {}` plus `?? 0` turned that into an equity put/call ratio of `0.00`, coloured green. The frontend then covered for both with hardcoded `FALLBACK` arrays — Fed Funds 5.33%, BTC $67,420, ES 5787.50 — rendered through the same markup as live data. The rules now: **a connector reports its own health each cycle** (`onStooqHealth`; `startConnector` only records what `start()` returned once, and no longer overwrites a failure the connector already reported), **an unavailable value is `null`, not `0`** (`CBOEData.putCall*`, with `putCallUnavailable` saying why), and **a panel with no data names the missing source** instead of inventing one. This is not the `synthetic: true` case — simulated prints keep the terminal functional and are excluded from the track record by name; a hardcoded Fed Funds rate has neither role nor exclusion.
- **`.env` was loaded after the import graph, so every key in it was invisible — and the terminal reported the connectors as `connected` anyway.** `config()` was called in `server.ts`'s statement body, below the imports. With `module: commonjs`, TypeScript compiles imports to `require` calls in source order and evaluates each module fully before the importer's body runs, so every module-level `process.env.X` in `ingestion/**` had already read an **empty** environment. The reporting then hid it rather than showing it: `startConnector` calls `missingCredentials()` at *call* time, when `process.env` is finally populated, concluded the credentials were present, and marked the source **`connected`** — while the connector had skipped at import time for want of the same key. Observed with three real keys in `backend/.env`: `/api/health` said `fred connected` and `finnhub connected` while the log said `[fred] No key — skipped` and carried no `[finnhub]` line at all. Render injects real environment variables before the process starts, so this never bit in production; it bit every developer with a `.env`, and it bit them by lying. `import 'dotenv/config'` is now the **first line** of `server.ts` and `dotenvOrder.test.ts` fails if it moves below the first local import (verified by moving it). **The mirror image was in FRED**, found the same way: one series discontinued upstream (`GOLDAMGBD228NLBM`) made it report `ok: false`, so `/api/health` showed the whole source red while nine of ten series filled the panel — and `fredKey.test.ts` *asserted* that behaviour under a comment explaining why it was wrong. A partial failure is now `ok` **and** `degraded`, and `connectorNotes` carries the reason to `sourceNotes` — the "connected but degraded" channel that already holds Polygon's missing-NBBO case — rather than to `sourceErrors`. Three states could not express "working, and incomplete".
- **Two WebSocket handlers ended `} catch {}`.** A frame that failed to parse was dropped with no counter, no log and no health signal, so a vendor changing its envelope — or a run of partial frames — produced a source that was `connected`, receiving bytes, and emitting **nothing**, while `/api/health` reported it working. That is this repo's recurring finding without even a zero to show for it: Stooq published quotes priced at zero and Cboe a ratio of 0.00, and a silently dropped frame publishes nothing at all, which is harder to notice rather than easier. `noteUnparsedFrame` counts per source and the count reaches `/api/health` through `sourceNotes` — the existing vocabulary for "connected but degraded", which is what carries Polygon's missing-NBBO case. It logs the first and then every five hundredth: a vendor that changes its envelope produces one failure per frame, and a log line per frame is its own outage.
- **A field the vendor did not send is not a zero, and that survived at field granularity in two connectors.** `deadSources.test.ts` closed this at *response* granularity — Stooq's challenge page stopped becoming twelve quotes priced at zero, Cboe's 403 stopped becoming a put/call ratio of 0.00 in green — but inside responses that had *succeeded*: `coinGecko.ts` wrote `?? 0` into every optional field, so a coin CoinGecko has no market data for was cached at **$0.00** with a 0.00% change and rendered through the same markup as a live row; and `cboe.ts` parsed each ratio with `parseFloat(today.equity_put_call_ratio ?? 0)`, and `parseFloat(0)` is `0`, not `NaN`, so a present row missing a ratio published one of 0.00 inside an `ok: true` block. A coin with no `current_price` is no longer cached at all (a record without a price is not a quote); its derived fields are `number | null` and the macro page renders `—`; a real zero is kept, because a real zero is data. A Cboe row missing any of the three ratios makes the block `ok: false` and names which. **CoinGecko also reported no health at all** — only a `console.error` — so a rate-limited deployment kept saying `connected` while serving an ageing cache, which is exactly the finding that gave Stooq `onStooqHealth`; it now reports every cycle and `429` reads as a rate limit rather than a generic failure. **Fifteen of eighteen connector `setInterval`s were missing `.unref()`.** Three had it, presumably added wherever someone hit the hang. The rest held the Node event loop open, so any process importing a connector and expecting to exit — a CLI, a test, a one-shot script — waited forever on a timer that would never matter to it. `missingIsNotZero.test.ts` found it by hanging, and now guards it by walking to each `setInterval`'s matching close paren (stopping at the first `;` hides `.unref()` on a multi-line poller — it hid two).
- **`/api/chain` answered every failure with a fabricated chain.** `buildMockChain` produced twenty strikes of `Math.random()` — bids, asks, volume, open interest, gamma, theta, vega and **implied volatility** — around a hardcoded 2024 spot map (SPY 580, NVDA 140, TSLA 250, SPX 5800), and it was returned in three cases: no `TRADIER_TOKEN`, a Tradier error of *any* kind, and — on `/expirations` — with **no marker at all**, because that response carries no `source` field. So a revoked token, a rate limit or a timeout produced a complete chain of invented prices behind `requireAuth`, the tier this repo reserves for entitled vendor data. That is `deadSources.test.ts`'s finding applied to a route rather than a connector: a source that is down must never present itself as data. The numbers were not internally consistent either — `bid` and `ask` drew **independent** random terms, so ask came in below bid on roughly half the strikes; `Math.max(0, …)` flattened a whole wing to a zero bid *and* a zero ask; and a call's `delta` is `0.5 - (k - spot) / (spot * 0.1)`, unbounded below, so far-OTM calls carried deltas past -3. Its spot map disagreed with the frontend's deleted one about NVDA by a factor of ten, the same ticker either side of a split. **Deleted rather than flagged**, like `generateSeedFlow`, `generateDarkPool` and `generateQuotes`: flagging would not have helped, because `/api/chain` is never served to demo traffic, so the mock could only ever reach a signed-in reader with every reason to think the chain was real. No credential is now a 503 naming `TRADIER_TOKEN` (the contract `markNoCredentials()` gives every connector), a vendor failure is a 502 carrying the vendor's own words through `describeHttpError`, and `/expirations` labels its `source`. Nothing in the frontend calls this route, which is when a fabricator is cheapest to remove.

- **A polling terminal could sign itself out.** `optionalAuth` called `supabase.auth.getUser()` on **every request**. When it limits, `getUser` errors, the `catch` swallows it, `req.user` stays undefined, and the request 401s: a working session silently signed out by its own polling, reported to the reader as `REFUSED — the backend did not accept this session`. A short-lived cache of **successful** verifications fixes it, and three properties make the trade honest. **Only successes are cached** — a failure may be Supabase being unreachable rather than the token being bad, and caching that would lock a valid session out for the whole TTL. **An entry never outlives the token**: the JWT's `exp` is decoded (never *trusted* — Supabase verified the signature before the entry existed) and can only *shorten* the entry, so a token expiring in one second is not honoured for thirty. **The key is a sha256 of the token, not the token**: it is already in memory because it arrived in a header, but a map keyed by raw credentials is one heap dump or one careless log away from every live session. The cost is a bounded revocation window, and `AUTH_CACHE_TTL_SECONDS` (declared in `render.yaml`, default 30) is the dial — `0` disables the cache and restores exactly the previous behaviour. `authenticateSocket` shares it, because `lib/socket.ts` passes `auth` as a callback and re-verifies on every reconnect, so a flapping connection would otherwise hammer the same endpoint until it limits. - **The rate limiter counted a header the caller writes, so it never fired.** `getKey` read `req.headers['x-forwarded-for'].split(',')[0]` — the **leftmost** entry. `X-Forwarded-For` grows left to right, each proxy appending the address it received the request *from*, so the leftmost entry is whatever the caller sent and everything to its right was written by a proxy. The known consequence was that an unrelated missing key blocked every grade — `tools/collection/doctor.ts` largely exists to say so. The unrecorded one: **no graded outcome said where its price came from.** With exactly one possible source that was recoverable by knowing the deployment; with more than one it would not be, and a track record whose rows cannot name the vendor that priced them cannot be audited afterwards. So `SpotLookup` is now `MarkLookup` returning a `Mark` — `{ price, source, rightsClass }` — which makes it **structurally impossible to record a mark without its provenance**, the same move as making `SpotQuote.change` nullable so the type could express the honest answer. `OutcomeRecord` gains `entryMarkSource`/`exitMarkSource`, both stores round-trip them, and `20260915090000_mark_source.sql` adds the columns with `signal_outcomes_mark_has_source` — a mark without a source is not recordable, the same shape as `signal_outcomes_ungraded_has_reason` refusing an UNGRADED row with no stated reason. That constraint is `not valid`: rows written before it have marks and no source, and validating against them would either fail the migration or invite a backfill that *invents* provenance, which is the thing the column exists to prevent. The two are attributed independently because they can genuinely differ — a vendor can drop out between registration and a checkpoint, and an excursion measured across two price sources is worth being able to spot rather than never. **The registry is one entry long, and that is the finding, not an omission.** Of everything here that can price an underlying: Finnhub is `PROHIBITED` for PERSIST by its own quoted redistribution clause, Yahoo is `PROHIBITED` for DISPLAY before the question arises, Polygon's plan on this deployment is entitled to end-of-day aggregates only — which cannot mark an M15 checkpoint — and Tradier has no token here and no REST quote helper written. **A vendor path that has never returned a price is not a fallback; it is a check with nothing to check**, so Tradier was deliberately not registered against a mocked response. The *mechanism* is ranked and the *registry* is short, and those are different claims — `markSources.test.ts` asserts `registeredMarkSources()` equals exactly `['twelvedata']` so the list cannot grow silently and let "ranked list" imply a plurality that is not there. **The ordering is derived from rights, and the obvious filter was the wrong one.** `classifySource(s, 'PERSIST', mode).allowed` is false for anything short of affirmatively PERMITTED, so filtering on it would have dropped Twelve Data and left the grader with no mark source at all — silently turning the only working path off. The established decision is the doctor's check 4b: *report the uncertainty, do not refuse it*, mirroring the connector gate, which refuses `PROHIBITED` only. So `PERMITTED` ranks above `UNVERIFIED`, `PROHIBITED` is never registered, and the class in force is written onto every row it prices; a test asserts `.allowed` really is `false` for the source being used, so the reason the tempting filter is wrong stays visible. **Check 4 stopped naming a variable.** It reported `TWELVE_DATA_API_KEY is unset` as *the* blocker; it now reports the registry — each candidate, its rights class, whether its credentials are set, and which of the two is the obstacle, because "no mark source" sends an operator hunting for a setting that may not be the one missing, and a source refused on rights will not start when a key is supplied. `/api/health` carries the same standings. **Two guards fired during this change and both were right.** `finnhubSpot.test.ts`'s "the connector does not reach the grader" predicted its own end — *"if a fallback is ever added to `getSpotPrice`, this fails"* — and it did. It is re-pointed rather than deleted, and is strictly stronger for it: instead of hoping the string `finnhub` stays outside a 300-character window, every registered source is classified and none may be `PROHIBITED` for PERSIST in either mode. `collectionDoctor.test.ts`'s mark test carried the same warning about going stale "in the least visible way" and got the same treatment. And a guard caught a defect written **in this change**: `markSourceStandings(env)` called `resolveBusinessMode()` with no argument, so it read `process.env` and quietly ignored the environment it had been handed — found by the test that passes a bad mode in `env` and watched the real process environment answer instead. Five mutations confirm the rest bites: registering Finnhub (caught by four tests), dropping the source from the recorded outcome, swapping the rank filter for `.allowed`, giving the registry the wrong variable name, and reverting check 4 to one env var. **What is still true.** One usable source means one refusal still grades nothing, so this buys auditability now and resilience only when a second source exists — 1.3 is what puts Tradier in, and it would rank above Twelve Data automatically. `resolveMark` deliberately does not check credentials: a source with no key has an empty cache and returns `null`, so it is skipped by the same branch that skips a source with no price for the symbol, and testing the key as well would put one fact in two places and invite them to disagree.

- **The backend has had a "connected but degraded" vocabulary for weeks, and nothing in the browser had ever read it.** `sourceNotes` was introduced with the FRED partial-failure fix — the note above calls it "the 'connected but degraded' channel that already holds Polygon's missing-NBBO case" — and it has since accumulated the unparsed-frame counters and, from the entitlement probe, a line saying the vendor refuses the key of a source that is otherwise contributing. `grep -rn sourceNotes frontend/` returned **nothing at all**: the `Health` interface in `app/settings/page.tsx` declared `sources`, `sourceErrors` and `rightsRefusals`, and the page rendered three channels out of a payload carrying four. The one it dropped is the one that says *this is arriving and it is qualified*. So Polygon could stream trades with every NBBO lookup refused — every print non-directional, which is the exact case `polygonQuoteNote` was written for — and the settings page reported it as **`✓ LIVE`**, in green. Measured, by mutating the fix back out: `polygon ✓ LIVE entitlement refused: HTTP 403 — NOT_AUTHORIZED`, the contradiction rendered on one row. **The fix is not a new field.** The tempting move was a derived `disposition` map merging state, errors, notes and entitlement into one verdict — and that would be a *seventh* channel answering a question three already answer, which is the failure this file records two notes above: two writers on one health field, and the loser was the truth. A derived field drifts from its inputs the first time one of them changes. The backend already says the thing; the browser simply was not reading it. So `sourceNotes` is rendered, in its own line and its own colour rather than concatenated onto `sourceErrors` — **an error is why nothing is arriving, a note is a qualification on what is, and a source can carry both** — and `connected` **plus a note** renders `◐ DEGRADED` instead of `✓ LIVE`. `DEGRADED` is deliberately not a fifth backend state: `sources` has four, this is what two of the existing fields mean together, and deciding it in the renderer is what keeps it from becoming another writer. `frontend/test/degradedSources.test.tsx` holds four claims, and the second matters as much as the first: a clean source is still plainly live, because a degraded marker that is always on is a marker nobody reads. It also covers a payload with no `sourceNotes` key at all, since the page predates the field and an older backend still answers. Two mutations confirm it bites — ignoring the note when choosing the badge, and dropping the note text — failing one test and two respectively. **What this does not touch:** `entitlement` and `markSources` are also unread in the browser. That is deliberate rather than pending — the entitlement verdict already reaches this page through the note channel, and a second rendering of the same fact is how two writers start; `markSources` belongs with the track record, which has nothing to show yet.

- **The table built to stop a flattering hit rate had never had a row written to it.** `collection_gaps` shipped complete: a migration with three CHECK constraints, a `CollectionGap` type, a `GapKind` union carrying a paragraph on why its members are different facts, and `recordGap`/`listGaps` implemented in **both** stores. `grep -rn recordGap src/` found the two implementations and **no caller** — not one, ever. And the paragraph in `types.ts` says exactly what that costs: *"Outages cluster in volatile sessions, because rate limits bite hardest when volume spikes — exactly the periods where a signal would be tested hardest. Silently dropping them removes the hard cases and makes any hit rate computed over the window flattering."* So the apparatus built to expose that bias had recorded nothing, and a track record computed today would carry it. This is the `sourceNotes` finding in a worse place: there, a populated channel nobody read; here, a channel nobody wrote. `persistence/coverage.ts` is the missing writer, ticking on the grader's existing 60-second timer. **`MARKET_CLOSED` is deliberately never emitted, though the union offers it.** Deciding a window was benignly shut needs a holiday calendar this codebase does not have, and this file already records what happens without one — a `MARKET OPEN` indicator over "a weekday-and-clock check with no holiday calendar: a green dot on Thanksgiving". The failure direction settles it: mislabelling a real outage as a closure turns missing data into data nobody expected, which is the flattering direction; an honest `NOT_OBSERVED` over a shut market overstates the gap, which costs a reader's time and nothing else. A guard asserts the string never appears as a constructed verdict. **Contiguous windows are one row, extended under a stable id**, because a 60-second tick writing a row per tick is 1,440 rows a day and a table nobody reads — and that surfaced a real disagreement between the stores: `supabaseStore.recordGap` **upserts** on `id` and `memoryStore.recordGap` **pushed**, so an open gap re-recorded as it extended was one row in Postgres and one row per tick in memory. The tests drive the in-memory store, so the difference would never have shown up in them. A store seam that behaves differently under test than in production is worse than no seam; memory upserts now, and a test holds them to the same answer. **What "collecting" means here is deliberately narrow:** not "the process is up" — a process with every connector disabled is running perfectly and observing nothing, which is the whole case — and not "any source is connected", since CBOE and FRED being up says nothing about whether an options print could have been recorded. It asks only about the sources that could be persisted, and a guard holds that list to the doctor's `RECORDABLE_SOURCES`, because a source that can be recorded but is not counted makes a productive window look like an outage and one counted but not recordable does the reverse. The first tick writes nothing and only establishes a baseline; there is no window before it, and inventing one dates the gap to the epoch. **2.3 of the roadmap — "record the entitlement state on every persisted signal" — needed no code and is closed as such.** `SignalRecord` already carries `source`, `datasetId`, `rightsClass` and `synthetic` per row. The entitlement *verdict* is a moment-in-time fact about a vendor, not a property of a signal, and stapling a mutable probe result onto an append-only row would be the wrong shape entirely.

- **DEX, a same-day lens, a gamma flip that was never one, and the last `Math.random()` in the tree.** Cboe's chain carries per-contract `delta` alongside `gamma`, `open_interest` and `iv`, so **dollar delta is as direct a computation as GEX** and is now aggregated per strike beside it. The difference between them is the whole point and it is easy to get backwards: **gamma is positive for calls and puts alike**, so `gex`'s call-positive / put-negative split is an assumption *expressed* as arithmetic — a book short both. **Delta already carries its own sign**, so imposing a second one flips the puts twice and reports a book that is the mirror of the tape. `dex` therefore applies no convention at all, and is named as what it is: what the open interest is long or short, **not** "dealer delta exposure". It also uses **one** factor of spot where gamma uses two — delta is already a share count, while gamma is a rate of change of delta and the second spot is what scales a $1 move into a 1%. Both mistakes are one character apart from correct and both have tests. **Vanna and charm are refused, not deferred.** Cboe does not publish them, and deriving them means recovering `d1` by inverting Cboe's own delta — importing every assumption in a pricing model this codebase does not have, silently, with no way to state what was assumed. A repo whose rule is *an invented number is a finding until justified* does not ship a second-order greek derived from an inverted first-order one. The payload says so in `assumptions.secondOrder`, next to `assumptions.dealerPositioning`, which states the thing every vendor in this category ships bare: **GEX is modelled, not observed** — a public chain shows greeks and open interest and says nothing about who is short which contract. That is the same move as `synthetic`, `side: AMBIGUOUS` and `INSUFFICIENT_SAMPLE`, and it costs one field. **The gamma flip is now `null`, with a reason.** It was `the first strike i where levels[i].gex > 0 and levels[i+1].gex < 0` — the first sign change in a strike-sorted array, weighted by nothing. Measured against a live AAPL chain on 2026-09-15 with spot at **331.75**, that returned **80**: a strike 76% below spot carrying **$1,420** of the chain's **$1.45bn**. The obvious replacement is not obviously right either — a cumulative-sum crossing gives **100** on the same chain, still 70% below spot, and crosses more than once because the tails are noisy; the method the vendors describe re-evaluates total gamma at hypothetical spot levels, which is a third computation. **Three candidate numbers for one label and no established basis to choose**, so nothing is published and `flipUnavailable` says why — the `putCallUnavailable` and `INSUFFICIENT_SAMPLE` pattern. A guard keeps the old rule from coming back. **`generateSyntheticGEX` is deleted, and there were two of it.** It built 31 strikes from `Math.random()` over a hardcoded **2024** spot map (`SPX: 5800`, `NVDA: 140`) — the same stale map this file already caught in the ticker tape — and seeded four symbols with it at boot. The second instance was worse: a **60-second timer** that overwrote `gexCache` for SPX/SPY/QQQ/NVDA with freshly randomised levels, into the very cache `getGEXLevels` reads as *the last real chain*. It is the same shape as `buildMockChain`, `generateSeedFlow`, `generateDarkPool` and `generateQuotes`, all deleted for the same reason. It was also already being refused — `GEXChart` treats `realData === false` as unavailable and draws nothing — so those numbers existed **solely to be thrown away**, with a stale price map left in the tree for the next caller to pick up. An empty list is the honest answer to "no chain has been received", and the page has an empty state for it. **0DTE is the chain's own trading date, and `null` is the ordinary answer.** Measured live on 2026-09-15: SPY carried 310 same-day contracts and SPX 484, while AAPL's nearest expiry was the **next** day — it had no 0DTE at all. A panel that quietly showed the nearest expiry instead would relabel tomorrow as today for most of the market. The date comes from the vendor's own timestamp rather than `new Date()`, because the server's clock can be in any timezone and the question is asked in the market's. **The zero-fill guard earned its keep mid-change.** The first version of the delta read was `numeric(r.delta) ?? 0`, and `defaultedReadings.test.ts` refused it by name — *"names a market reading (delta), where the bar is highest"*. It was right: an option's delta is never actually zero, so a contract the vendor sent none for would have been recorded as having no directional exposure, and **zero being the additive identity of the sum it feeds makes that invisible rather than harmless**. Deltaless contracts are now skipped for DEX and counted in `dexMissing`, published per strike, because a sum missing terms is not the same quantity as a complete one. Two of the ledger's own entries were also stale and are corrected: the `spotMap[symbol] ?? 100` registration described a function that no longer exists.

- **One label was covering two positions that disagree about direction, and the ledger had misnamed the example.** `guessSpread` returned `STRADDLE_STRANGLE` for **every** call-and-put pair at one expiry, ignoring `leg.side` entirely. That is only right when both legs are on the same side: a long call against a **short** put is a **risk reversal** — a directional bet financed by selling the other wing — and it is the opposite kind of position from a long strangle, which is a bet on movement in either direction. Both arrived under one name. `RISK_REVERSAL` now separates them, off `leg.side`, which `SignalLeg` has carried all along; no new data, no new vendor, four lines of classifier. **`AMBIGUOUS` is why this can refuse, and that is the load-bearing part.** The engine declines to infer a side without a fresh NBBO, and a structure *defined* by whether its legs oppose each other cannot be named from a leg with no polarity — so one `AMBIGUOUS` leg yields `UNKNOWN`. Naming it anyway would stamp a directional label on a position whose direction the engine has already refused to state, which is `side: AMBIGUOUS` being resolved to a guess one layer up. A `*_LEAN` **does** count as its polarity, and the reason is that the uncertainty is already priced: the ambiguity penalty lives in the score, and discounting it again here would double-count it. That decision needed a guard and did not have one — the mutation that stopped leans counting passed the whole suite, because nothing exercised a lean leg. A decision with no guard is a comment that drifts, so there is now a test that drives `BUY_LEAN` against `SELL_LEAN` and a lean against a firm side. Same-right structures are deliberately **not** routed through the polarity check: a vertical is named by its contracts alone, and making it unnameable because one leg was ambiguous would refuse an answer that never depended on direction. Butterflies, condors and everything beyond two legs stay `UNKNOWN` — they need grouping logic that does not exist, and nothing downstream reads `spreadGuess` to make a decision, so new union members would be cost with no reader. **And checking the premise found the misnomer.** The entry above — the one about grading the wrong leg — described its fixture as "a bought $102k SPY call alongside a $2.2k put, a bullish risk reversal". Driving that exact fixture through the engine reports `side=BUY` on **both** legs, because both are lifted at the ask, and `spreadGuess: STRADDLE_STRANGLE`. It is a **long strangle**. The finding it illustrates is untouched — the tracker really did read `legs[0]` and pair it with `signal.side`, and the fix stands — but the structure was misnamed in the one entry about reading structures correctly, and the same words had been copied into `outcome/types.ts` and `outcome.test.ts`'s docstring. All four are corrected. The lesson is the cheap one: the classifier existed, so the claim was checkable in about a minute, and nobody had checked it. **Four homes, because the engine is vendored:** `engine.ts` and `types.ts` on both sides of `backend/src/flow-engine/` ↔ `quantflow-modules/flow-engine/src/`, held byte-identical by `vendorMirror.test.ts`, plus the frontend's `spread_guess` union. The `spread_guess` column is plain `text` with no CHECK, so a new value needed no migration.
